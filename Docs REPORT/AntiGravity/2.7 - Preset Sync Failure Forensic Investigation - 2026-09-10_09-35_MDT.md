## Executive Summary

While running GS3 locally at `http://localhost:8080`, the user attempted normal Preset Sync and received the blocking failure dialog:
```text
Preset Sync failed: Push rejected. Double-check branch states or credential authorizations.
```
Subsequent attempts failed identically.

Forensic investigation of the codebase confirms:
1. **There is no Git CLI or local command-line push.** Preset Sync uses an HTTP `PUT` request to the GitHub REST Contents API (`PUT /repos/{owner}/{repo}/contents/presets.json`).
2. **Error Collapsing:** GS3's `sync.js` discards all HTTP status codes (401, 403, 404, 409, 422, 500) and response bodies from GitHub, collapsing every failure into the single hardcoded string above.
3. **Stage 2.6 did not cause this.** Neither `sync.js` presets handling nor `presets.js` was modified by Stage 2.6. This exact error is documented in `Docs REPORT/Tests/TESTING.md` §5.2 as a known, pre-existing unresolved bug.
4. **Primary Suspect:** A stale blob SHA in transient memory (`_state.presetsSha`) causing GitHub to reject the update with `409 Conflict` (`"presets.json does not match <sha>"`). The code does not refresh the SHA upon failure, causing 100% repeatable rejections on retries.

## B. What “Push rejected” Actually Means in GS3

1. **No Git CLI or command-line push:**  
   GS3 does **not** execute `git push`, invoke local Git binaries, or touch the local `.git` repository. Preset Sync is entirely an in-browser HTTP client calling the GitHub REST API.
2. **GitHub Contents API Endpoint:**  
   GS3 issues an HTTP `PUT` request to `https://api.github.com/repos/{owner}/{repo}/contents/presets.json`.
3. **Error Collapsing:**  
   `pushPresetsToRemote()` in `js/sync.js:265-275` evaluates only `if (res.ok)`. When GitHub returns any non-2xx HTTP status code (`401`, `403`, `404`, `409`, `422`, `500`), **the HTTP status code and GitHub's JSON error response are completely discarded**.  
   Instead, line 271 synthesizes the single hardcoded string:  
   `'Push rejected. Double-check branch states or credential authorizations.'`  
   Therefore, "Push", "branch states", and "credential authorizations" are developer phrasing in `sync.js`, not an error message returned by GitHub or Git.

## C. Most Likely Root Cause

**Primary Suspect: Stale Blob SHA Concurrency Conflict (HTTP 409 Conflict)**

* **Mechanism:**  
  GitHub's Contents API requires that updates to an existing file supply the exact blob `sha` of the current remote file. If `sha` is omitted or does not match the latest commit on `main`, GitHub rejects the write with **`409 Conflict`** (`"presets.json does not match <sha>"`).
* **Code State:**  
  1. `presetsSha` is stored **only in transient memory** (`_state.presetsSha` in `js/state.js:63`). It is never persisted to `localStorage`.
  2. It is populated on page load by `fetchPresetsSilently()`. If `fetchPresetsSilently()` failed or was skipped on boot, `presetsSha` is `null`.
  3. If `presets.json` was updated remotely (by another tab, another session, or a git push) after the page loaded, the in-memory `presetsSha` is stale.
  4. **The Critical Loop Defect:** When `pushPresetsToRemote` fails, **it does not refresh `presetsSha`**. If the user clicks Save/Sync again, `sync.js` resends the exact same stale SHA. This matches the human observation: *"The user then manually tried the normal Sync action again. It failed again."*
  5. This exact defect is documented as a known unresolved issue in `Docs REPORT/Tests/TESTING.md` §5.2.
